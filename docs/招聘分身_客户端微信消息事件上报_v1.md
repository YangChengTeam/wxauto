# 招聘分身客户端微信消息事件上报接口

## 背景

业务后端需要根据真实微信消息事件判断招聘计划的未回复跟进：

- 我方消息发送成功后，开始计算“多久未回复”。
- 候选人发来消息后，取消当前候选人的待跟进任务。
- 客户端只上报事实事件，不判断是否需要发送第二条消息。

## 接口

```http
POST /api/recruitment-agent/client/message-events
Authorization: Bearer <client_token>
Content-Type: application/json
```

该接口仅供 Windows 招聘分身客户端调用，使用客户端登录后拿到的 `client_token`。客户端账号需要具备 `talent:advance` 权限。

## 请求字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `eventId` | UUID string | 是 | 客户端生成的事件唯一 ID。断网重试必须保持不变，用于幂等。 |
| `candidateId` | UUID string | 是 | 劳小智候选人 / worker ID。 |
| `direction` | `outbound` / `inbound` | 是 | `outbound` 表示我方发给候选人；`inbound` 表示候选人发来消息。 |
| `messageType` | `text` / `image` / `voice` / `video` / `file` / `link` / `emoji` / `unknown` | 否 | 默认 `text`。 |
| `messageId` | string | 是 | 微信侧消息 ID；如果拿不到，用客户端本地稳定唯一 ID。长度 1–180。 |
| `commandId` | string | 否 | 我方消息如果来自 AI / 后端指令，带上对应 `commandId`。候选人入站消息不要传。 |
| `status` | `sent` / `received` | 否 | `outbound` 默认为 `sent`；`inbound` 默认为 `received`。 |
| `contentDigest` | string | 否 | 消息正文摘要，可传 SHA-256 / 截断摘要；不要上传完整聊天正文。 |
| `occurredAt` | ISO datetime with offset | 是 | 微信事件真实发生时间，例如 `2026-08-24T09:00:00+08:00`。 |
| `metadata` | object | 否 | 客户端补充信息，禁止放 token、密码、完整聊天正文等敏感数据。 |

## 我方消息发送成功示例

```json
{
  "eventId": "9f81f4c4-4c30-4a0a-9d74-39b36a8d86d4",
  "candidateId": "6052b11b-d0a6-4ebb-a32d-e077552f041c",
  "direction": "outbound",
  "messageType": "text",
  "messageId": "wxmsg_local_20260824090000001",
  "commandId": "cmd_20260824_001",
  "status": "sent",
  "contentDigest": "sha256:8d969eef6ecad3c29a3a629280e686cf",
  "occurredAt": "2026-08-24T09:00:00+08:00"
}
```

后端处理：

1. 落库消息事件。
2. 找到该候选人的有效招聘计划任务。
3. 取消旧的待执行未回复跟进。
4. 根据计划配置重新生成 FOLLOW_UP，例如配置 4 小时，则跟进时间为 `occurredAt + 4 小时`。

## 候选人回复消息示例

```json
{
  "eventId": "ed5159c0-f00e-48c0-86c1-1463b3859109",
  "candidateId": "6052b11b-d0a6-4ebb-a32d-e077552f041c",
  "direction": "inbound",
  "messageType": "text",
  "messageId": "wxmsg_local_20260824125900001",
  "status": "received",
  "contentDigest": "sha256:1f3870be274f6c49b3e31a0c6728957f",
  "occurredAt": "2026-08-24T12:59:00+08:00"
}
```

后端处理：

1. 落库消息事件。
2. 找到该候选人的有效招聘计划任务。
3. 取消旧的待执行未回复跟进。
4. 不立即重新计时；等我方下一次 `outbound sent` 事件上报后，再重新开始未回复计时。

## 幂等规则

客户端需要保证：

- 同一次事件重试时 `eventId` 不变。
- 同一条微信消息的 `messageId` 稳定不变。

后端会按以下规则去重：

- `eventId` 重复：视为重复事件，直接返回成功。
- 同一招聘分身、同一候选人、同一方向、同一 `messageId` 重复：视为重复消息，直接返回成功。

## 响应示例

```json
{
  "accepted": true,
  "duplicate": false,
  "linked": true,
  "action": "schedule_follow_up",
  "supersededFollowUps": 1,
  "nextInstructionId": "0ef97ef2-7a3b-4c83-97aa-e94cf16f7b32",
  "eventId": "9f81f4c4-4c30-4a0a-9d74-39b36a8d86d4"
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `accepted` | 后端已接收事件。 |
| `duplicate` | 是否重复事件 / 重复消息。 |
| `linked` | 是否匹配到当前候选人的有效招聘计划任务。 |
| `action` | `schedule_follow_up`：已生成未回复跟进；`cancel_follow_up`：已取消待跟进；`none`：无需动作。 |
| `supersededFollowUps` | 本次取消的旧 FOLLOW_UP 数量。 |
| `nextInstructionId` | 新生成的 FOLLOW_UP 指令 ID；只有 `schedule_follow_up` 时可能返回。 |

## 对接注意事项

- 客户端不要自己判断“4 小时未回复要不要发第二条”，只上报真实事件。
- 客户端不要自己触发第二条跟进消息，避免和后端调度重复。
- `occurredAt` 必须使用微信事件真实发生时间，不要用补报时间。
- 不要上传完整聊天正文；如需排查，只传摘要或本地日志引用。
- 入站消息如果无法匹配 `candidateId`，本接口不要上报；应先完成联系人 / 候选人匹配。

## 客户端这一侧怎么落的（本仓实现说明）

### ⚠️ 路径前缀：本仓按 `/recruitment-agent/...` 发，**不带**上面那个 `/api`（线上实测）

契约正文写的是 `POST /api/recruitment-agent/client/message-events`。2026-08-24 后端部署后
对线上打了两发（都没带凭证）：

```text
POST https://api.laoxiaozhi.cn/recruitment-agent/client/message-events
  → 401 {"code":"CLIENT_TOKEN_REQUIRED","message":"需要登录招聘分身客户端"}   ← 就是这条路
POST https://api.laoxiaozhi.cn/api/recruitment-agent/client/message-events
  → 401 {"code":"UNAUTHORIZED","message":"需要登录"}                          ← 另一套网页鉴权
```

带上 `/api` 命中的是**网页会话**那道闸，客户端 Token 在那儿根本不作数——照契约字面写会
一直 401，而且错得不像路径错。业务后端 `src/app.ts` 就是 `app.use('/recruitment-agent', …)`，
同一个 base URL 上其余每条客户端接口（登录、换票、`/client/contacts`、`/client/candidates`）
也都没有 `/api`。

### 后端这一头（2026-08-24 已部署，`lxz_business_backend`）

对过一遍，两侧一致：

- 路由 `src/routes/recruitment-agent.ts`：`requireRecruitmentAgentClient` +
  `requireClientPermission('talent:advance')`，参数走 `ClientMessageEventSchema`（zod）。
- **去重键是 `eventId`（主键）+ 唯一索引 `(agentId, candidateId, direction, messageId)`**。
  我们的 `eventId` 正是从后三者派生的，两条去重线因此永远一致——换成随机 UUID 就会
  出现「主键不重、唯一索引重」的插入冲突。
- 字段宽度即建表宽度：`messageId` 180 / `commandId` 120 / `contentDigest` 128，
  `candidateId` 是 `workers.id`（uuid）。本机按这三个宽度自截（`commandId` 超长则**丢字段
  保事件**，截断只会得到一个对不上任何指令的假 ID）。
- 跟进时点用的是**我们报上去的 `occurredAt`**（`followUpDueAt(plan, occurredAt)`），不是后端
  收到的时刻——所以 `occurredAt` 的准头直接决定跟进早晚。
- 一段回复报多条 outbound 不会吃掉计划的跟进次数：每条只是 supersede 前一条再插一条，
  最后一条的时间生效；`followUpCount` 是执行时才涨的。
- `linked: false` = 这个候选人名下没有 `running`/`paused` 的招聘计划任务，事件照收不打回。

代码：`wxclient/gateway/message_events.py`（发件箱 + 上报）、`wxclient/gateway/sessions.py`
（`gateway_message_events` 表）、三个登记点见下。测试：`tests/test_gateway_message_events.py`。

| 事件 | 登记点 | `messageId` | 备注 |
| --- | --- | --- | --- |
| 候选人回话 | `GatewayRunner._note_inbound_messages`（由 `InboundLoop` 读到消息时回调） | 本机 `msg_id` 派生 | 「别再联系我了」也是一次回复（网关关键词拒绝闸 2026-09-19 已拆，这条消息照常派给 AI 端） |
| 自动回复发出 | `OutboundSender._note_outbound` | 队列任务 ID 派生 | 一段回复拆几段就报几条 |
| 计划指令发出 | `CommandExecutor._note_message_sent` | `command_id` 派生 | 带 `commandId`；只在队列回 `succeeded` 时报 |

四条规矩：

1. **先落本机发件箱，再由后台循环上报**（`MESSAGE_EVENT_FLUSH_INTERVAL_SECONDS`，20s）。
   上报走网络、网络会抖；抖一下就丢的代价是候选人明明回了话、四小时后还被追一条。
   记账也绝不能挡在微信动作前面。
2. **`eventId` 由内容派生**（`event_id_for`，uuid5），断网重投永远是同一个值。
3. **归不了位就不报**：候选人 ID 由本机按会话名反查（`contact_worker_id`），
   反查不到如实跳过，不编 ID 顶上。
4. **只走流程不真动微信（dry-run）的机器一条都不报**：`factory.py` 在
   `allow_real_actions` 为假时压根不建这个上报器。

不上传聊天正文：只带 `contentDigest` 摘要；`messageId` 也哈希过（本机 `msg_id` 里带着
候选人的备注名）。事件超过 24 小时没报出去会被清掉，并留一条 WARNING。

### 接口验证做到哪一步（2026-08-24）

后端部署当天对线上核过一遍，**除了「带真 Token 打通一次」以外都验了**：

```text
# 客户端这条路（本仓真实的 header 写法：authorization: Bearer …）
POST /recruitment-agent/client/message-events                （无凭证）→ 401 CLIENT_TOKEN_REQUIRED
POST /recruitment-agent/client/message-events                （假 Token）→ 401 CLIENT_TOKEN_INVALID
POST /api/recruitment-agent/client/message-events            （假 Token）→ 401 TOKEN_INVALID  ← 网页那道闸
```

401 从 `CLIENT_TOKEN_REQUIRED` 走到 `CLIENT_TOKEN_INVALID`，说明**路径、方法、header 名、
content-type 都对上了**，卡住的只剩「有没有一张真票」。请求体用的就是本仓 `build_event()`
的真实产出（三条：入站文本、出站自动回复、出站文件带 `commandId`），逐字拿线上那份
`ClientMessageEventSchema`（zod）离线 parse 过，**3/3 通过**。

**最后一步没做，是故意的**：客户端登录回 `409 ACTIVE_CLIENT_SESSION_EXISTS`——这个分身
另一台电脑（`LAPTOP-4L320UGE`）还占着会话。带 `replaceExistingSession=true` 能顶掉，但顶掉
之后那台机器会被清 Token、退回登录页（`wxclient/ui/auth.py` 就是这么写的：**不自动重登**），
中间自动回复是停的，得有人去那台机器上重新登一次。本仓自己的规矩就是「顶掉别人的设备
要问过人」，所以留给人点头。

（顺带：同账号的**网页**登录 `POST /auth/login` 回的是 `challengeRequired`（新设备邮箱验证码），
不是密码问题；而且网页 Token 也进不了 `/client/message-events`——那道闸只认客户端 Token。）
