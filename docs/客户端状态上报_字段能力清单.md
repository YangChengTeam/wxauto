# 客户端状态上报：哪些字段给得出、哪些给不出

> 面向：劳小智业务后端。对应契约 [`招聘分身_客户端认证与状态接口_v1.1.md`](招聘分身_客户端认证与状态接口_v1.1.md) §7 / §8。
> 结论都在真机 + 真后端（`https://api.laoxiaozhi.cn`）上实测过，2026-08-15。

## 结论

`PUT /recruitment-agent/client/wechat-uia/status` 现在**能过**，服务端返回 `stage: running`。
唯一一处将就：`wechatInstance.nickname` 客户端读不到，按用户裁决**填占位符 `-`**。

实测（同一份载荷，只差 nickname）：

```
无 nickname  → 400 VALIDATION_ERROR  details[0].path = ["wechatInstance","nickname"]
nickname="-" → 200 {"accepted":true,"wechatUiaStatus":"connected","agentStatus":"running","stage":"running"}
```

## 给得出的字段

| 字段 | 来源 |
|---|---|
| `status` | 只读窗口探测，15 秒一拍 |
| `failure.{code,message,retryable}` | 失败时必带，取自 §8 失败码表中的 4 个（见下） |
| `capabilityStatus` | `passed`/`limited`/`failed`，由客户端逐能力表算出。只走流程不真发消息的机器如实报 `limited` |
| `wechatInstance.processVersion` | 微信 exe 的文件版本，如 `4.1.12.26`。读不到时填 `-`（服务端把它也设成了必填，少一个字段整条 connected 就白发） |
| `wechatInstance.accountRef` | 真实 wxid 的 SHA-256（算法见下），不可逆、跨机稳定 |
| `wechatInstance.accountMask` | 形如 `wxid_****m12` |
| `eventId` / `occurredAt` | UUID 幂等键 + UTC ISO-8601 带毫秒。同一 `eventId` 重发返回同一结果，已验证 |

## 给不出的字段

| 字段 | 为什么 |
|---|---|
| `wechatInstance.nickname` | 微信 4.x 主窗口的 UIA 控件树里没有自己的昵称；账号目录下只有加密 sqlite。唯一读法是驱动界面点开「个人信息」面板——会在用户正用微信时抢焦点，且现成的 vendor 实现在这版微信上已失效（面板类名对不上）。**现在填 `-`**，一眼看得出是「没读到」；绝不拿分身名之类的东西冒充，那会让企业端显示一个看着像真的、其实是假的微信身份 |

> `-` 是这份契约里「读不到」的统一约定（`nickname` 恒为 `-`，`processVersion` 仅在读不到时）。
> 后端若要按 `processVersion` 做版本门禁，请把 `-` 当作「未知」处理，别当成版本号解析。

**建议后端把 `wechatInstance` 整体改成可选**：一台电脑同时开了两个微信、或系统不让枚举进程文件时，
客户端连 `accountRef` 都拿不到（认不出该用哪个账号时我们**不猜**），这种机器现在会 100% 卡在 400。
占用检查按「有 `accountRef` 才查」处理即可。

## 枚举里客户端不会出现的值

不是没实现，是这台机器上**判定不出来**。后端做状态机和文案时按这个来，别等一个永远不来的值。

| 枚举 / 失败码 | 会不会报 | 为什么 |
|---|---|---|
| `status = not_connected` | 不报 | 客户端只在探测出结果后才上报；「还没连」由服务端在登录时初始化 |
| `status = connecting` | 不报 | 探测是一次性只读快照（找进程 → 找主窗口 → 看控件树），没有可观察的「连接中」阶段。所以 `stage=wechat_uia_connecting` 实际不会出现 |
| `WECHAT_UIA_PROCESS_NOT_FOUND` | 会报 | 没有微信进程 / 窗口 |
| `WECHAT_UIA_ACCOUNT_NOT_LOGGED_IN` | 会报 | 停在登录（扫码）窗口 |
| `WECHAT_UIA_WINDOW_UNAVAILABLE` | 会报 | 窗口在但控件树没暴露，或探测本身失败 |
| `WECHAT_UIA_CONNECTION_LOST` | 会报 | 连过又断，配 `status=disconnected` |
| `WECHAT_UIA_PERMISSION_DENIED` | 不报 | 目前区分不出「权限不足」和「控件树没暴露」，一律归到 `WINDOW_UNAVAILABLE` |
| `WECHAT_UIA_CONNECT_TIMEOUT` | 不报 | 同上：没有「连接中」阶段，也就没有超时 |
| `WECHAT_UIA_VERSION_UNSUPPORTED` | 不报 | 客户端没有「支持哪些微信版本」的白名单。建议服务端拿 `processVersion` 判——判定规则本来也该在服务端统一 |
| `WECHAT_UIA_ACCOUNT_IN_USE` | 不报 | 只有服务端知道别的分身占没占。客户端报这个码等于替服务端下结论 |
| `CAPABILITY_CHECK_FAILED` | 不报 | 同一件事已由 `capabilityStatus=failed` 表达，不给两套说法 |

## accountRef 的算法

```
原始账号目录   xwechat_files\wxid_6shq4q0wu92m12_c174\...   ← 从微信进程打开的文件里读到，不碰界面
去掉安装后缀   wxid_6shq4q0wu92m12                          ← _c174 是这台电脑这次安装的编号
accountRef     sha256("lxz-wechat-account:v1:" + wxid)[:32]
accountMask    wxid_****m12
```

**为什么要去掉 `_c174`**：同一个微信在两台电脑上登录时这个后缀不同。留着的话同一个账号会算出
两个 `accountRef`，服务端那条「一个微信只能被一个启用中的分身占用」**永远不会触发**。
后端要换算法（带你们的盐、或要求原始 wxid）就说，客户端这边是一行的事。

实现在 `wxclient/uia_probe/account.py`。

## 客户端状态那条接口（`PUT /client/status`，无缺口）

| status | reason | 什么时候 |
|---|---|---|
| `online` | `client_start` | 重开客户端、接上上次的会话 |
| `online` | `service_running` | 网关起来了 / 异常之后恢复 |
| `error` | `runtime_error` | 有会话但网关起不来 |
| `offline` | `user_logout` | 用户退出登录，**在撤销会话之前同步送达** |
| `offline` | `client_shutdown` | 退出程序前送出，最多等 3 秒 |
